SEC.01

$为什么存在

现代笔记本很少只有「一个网络」：WiFi 在办公网，USB 坞是第二条上行，VPN 的 TUN 设备、Tailscale、Docker 网桥共存于同一张路由表，还常被全局 TUN 代理劫持。niclane 把每张网卡变成独立车道：一个出口硬绑定到指定网卡的本地代理监听器。车道之间互不可见、不共享路由、绝不串线。v0.4.0 起一条车道可以持有有序候选——切换只发生在该车道自己声明过的候选之间；候选全灭且 strict 时立即拒绝新连接，仍然绝不静默改道到车道之外。

SEC.02

$能力清单

F01
📌

出口硬绑定

Linux 用 SO_BINDTODEVICE，macOS 用 IP_BOUND_IF，把 socket 钉死在一张网卡上。

F02
🚧

Fail-closed

监视器每 2 秒复查接口；不健康且 strict 时，拨号直接拒——没有兜底，没有泄漏。

F03
🔎

车道内 DNS

域名解析经本车道拨出，支持 DoH（AliDNS / Cloudflare），DNS 不外泄。

F04
⛓️

上游代理链

可链 socks5:// 或 http:// 上游——上游连接本身也走本车道。

F05
📊

全量计数

连接数、拒绝数、双向字节、DNS 查询、UDP 报文，Prometheus 格式导出。

F06
📦

UDP ASSOCIATE

RFC 1928 UDP 中继经车道绑定的 UDP socket 转发。

F07
🔀

候选车道与自动故障转移

一条车道持有有序的 (interface, upstream) 候选，不再只能是钉死的一张网卡。每条客户端连接在 resolve + dial + UDP 全程锁定同一个候选；排序按优先级 → 探测延迟 → 配置顺序。每个候选都经自己的网卡做健康探测，连续 2 次失败判死、1 次成功即复活；strict: true 时无一健康就 fail-closed。

F08
🧭

Linux 自动发现

discover: 枚举选中网卡，解析每张网卡自己的网关（via 覆盖 → /proc/net/route → systemd-networkd 租约 → nmcli），只对那个网关做 TCP 端口探测——不扫子网、不碰全局默认路由、不猜厂商或 MAC。发现的候选排在静态候选之后（权重 100 对 1000），端口不再应答就自动消失。端口清单可维护：全局 discovery.ports（默认 [10808, 10809, 7890, 7891]）加每车道 discover.ports 覆盖并去重；SIGHUP 改了全局清单只重启带 discover: 块的车道。

F09
⚖️

失败分类学

只有传输层失败（拨号错误、超时、握手 IO、fail-closed 拒绝）才触发转移。上游的应用层拒绝（SOCKS5 reply ≠ 0、HTTP CONNECT 非 2xx）原样回给客户端，永不扣候选的健康分——上游说「不许」和链路说「不通」是两件事，混为一谈会让好候选被冤枉判死。

F10
🔬

候选可见

niclane discover 打出当前扫描结果（网卡、上游、来源、健康、延迟）；test 与 status 输出候选感知，/status 在 candidates 下暴露每候选状态。旧的单网卡车道语义不变，而 interface/upstream 与 candidates/discover 混写会被校验直接拒。
