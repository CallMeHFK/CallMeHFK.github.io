SEC.01

$为什么存在

个人树莓派 / 家庭服务器实验仓库。README 自己的定性是：「代码以「能跑起来」为主，各子项目彼此独立，没有统一的构建系统。」当前活跃开发在 voicekit/——浏览器（iPhone / 桌面）和语音助手开一场实时语音通话：你说中文，助手听懂、回答、用语音说回来。

和普通「语音壳 + 大模型」的区别在于：LLM 后端是跑在树莓派上的 pi / sol-pi CLI agent，所以它不只是聊天——它真的能在 Pi 上执行工具（比如你说「列一下当前目录有哪些文件」，它会去跑 ls）。语音链路基于 LiveKit：信令走 HTTPS/WSS，媒体走 WebRTC（UDP）。

SEC.02

$能力清单

F01
🎙️

四段语音链路，每段都可换后端

VAD 用 livekit 内置的本地 silero（inference.VAD）；STT 走 SiliconFlow ASR，模型 XingChenAGI/XingChenGSR-V1.0，非流式；LLM 是 GatewayLLM 回退链；TTS 是 MiMo mimo-v2.5-tts，SSE 流式返回 pcm16 / 24 kHz 单声道，默认音色「茉莉」。

F02
🔗

LLM 回退链

VOICEKIT_LLM_BACKENDS 逗号分隔，默认 solpi,newapi,siliconflow,platform。其中 solpi 就是 bridge/index.ts 起的 :8790，经 ssh 打到派上的 pi-acp（ACP 协议，流式加工具）；newapi 是局域网 OpenAI 兼容网关，无 key 就跳过该后端。[llm] solpi failed: 是判断「桥有没有真的接上 Pi」的第一现场。

F03
🪜

桥的降级链是写死的

pi-acp（ssh ACP 常驻会话，流式 + 工具）→ pi -p（ssh 一次性，桥按句切块）→ error。降到第二档就失去流式与工具，所以「能不能停在第一档」是这套东西好不好用的分水岭。

F04
🚪

网关是唯一对外入口

gateway.py 在 8445 上跑 aiohttp + TLS：/login /logout 发 HMAC cookie，/tk 铸 LiveKit token，/livekit/** 做 wss + http 反向代理。防爆破：同一客户端 IP 10 分钟内 ≥5 次失败就 429 锁 10 分钟。token 注册表存 sha256，TTL 2 小时。

F05
🧭

媒体绕开网关，这是设计不是漏洞

livekit-server 用 docker --network host 起：TCP 7880 信令、TCP 7881 媒体兜底、UDP 7882 媒体走 ICE 直连，不经过 8445。所以端口暴露规则是明确的三行——8445 TCP ✅ 唯一对外入口，7882 UDP ✅ 媒体，7880 / 7881 TCP ❌ 绝对不要开。

F06
📞

桥的 HTTP 面很窄

POST /utterance 用 SSE 回 {"type":"chunk"} … {"type":"done"} / {"type":"error"}，加一个 GET /health。BRIDGE_PORT 默认 8790 且只绑 127.0.0.1。

F07
⏱️

端点静音是调出来的，别再往上调

agent.py 的 turn_handling 把端点静音压到 min_delay 0.3 / max_delay 2.5。README 在这一条后面直接写了「别再往上调」——因为非流式 STT 要等一段话说完才出整段文本，再放宽延迟就直接变成「说完半天没反应」。

F08
🔧

工具能力不来自 livekit

GatewayLLM 不支持工具调用——tools 参数会被忽略并打印一行 warning。工具能力来自 pi-acp 那一侧的 agent，不来自 livekit 的 function calling。这条写在 README 的「其它」里，是为了防止下一个人去调 tools=。

F09
📓

19 条评审发现，全部有归宿

docs/issues/ 是 0001–0019 的编号台账，每条按 Severity / Component / Evidence（带 file:line）/ How it manifests / Proposed fix / Status 六段写。当前状态：18 条 resolved（分别并到 51f4f72 与 87fae63）+ 1 条 documented-only（残余风险已接受）。三条远端分支 ahead=0，全部已合并，没有未发布的东西。

F10
🧩

Python + TypeScript 混血

42 个跟踪文件、约 4,291 行手写代码：voicekit/*.py 1,910 行（plugins.py 748、gateway.py 433、common.py 179、login_page.py 85、agent.py 72……）加 voicekit/bridge 的 TypeScript 841 行（index.ts 与 drivers/{abort,acp,cli,ssh,types}.ts）。GitHub 把它标成 Python 是不准的。

SEC.05

$路线

  • 已落地

    voicekit 全链路（网关 + LiveKit + worker + 桥）、流式 TTS / ASR、完整迁移到 Pi。HEAD 提交即 voicekit: streaming TTS/ASR + full Pi migration

  • 已落地

    两轮评审的 19 条发现里 18 条已修并合入 main：桥的 capture 上限 / 泄漏 / reaper / send-mutex / ssh-env、网关 ws pump、worker backend lock、livekit keys。抽查过工作树确认真在：bridge/drivers/cli.ts:9 是 const CAPTURE_LIMIT = 1024 * 1024;，bridge/drivers/ssh.ts:8 是 export const SSH_HOST = process.env.PI_SSH_HOST ?? 'leo@100.100.231.92';

  • 边界

    本仓库没有 LICENSE，连散文里也没声明过任何许可——比「README 声明 MIT 但没有 LICENSE 文件」更弱一档，法律上是未授权。也没有版本、没有 tag、没有 release、没有 CI 工作流，0 项自动化测试：voicekit/test_plugins.py 名字像测试，实际是 0 个 def test_、4 个 assert 的手工离线联调脚本（docstring 写的是「TTS 出音 → STT 转回文本 → LLM 接一句」）。真正的验证面是 e2e.py（142 行）与 e2e_tailnet.py（191 行）两个手工 e2e，本页写作时未执行——跑它们需要 docker LiveKit、能 ssh 到的 Pi、三个 systemd user unit 和付费的 MIMO_KEY / SILICONFLOW_KEY

  • 边界

    根 README 记的比仓库里有的多。README 的子项目表列了 5 个目录加 4 个松散脚本，而 git ls-files 的顶层只有 docs、.gitignore、README.md、voicekit 四项——voice-agent-phone/、voice-agent/、tts-service/、relay_newapi.py、rp.sh、test_phone_e2e.py 与 .pi-* 都不在仓库里。README 还链到 agent-chatroom/README.md，那条链接在仓库内是 404——它已经是独立仓库了。所以关于那些子项目的任何说法，都无法从这个仓库验证

  • 边界

    本项目最重要的一条安全约束（README 原话）：不传 --keys 时 --dev 会退回占位符 devkey / secret，等于任何人都能自签一个 JWT 直连 7880 进房间，完全绕过 8445 的登录。start.sh 的兜底分支会自动带 --keys，并删除缺 --keys 的旧容器

  • 边界

    已接受的残余风险（台账 0009）：LiveKit 容器的启动参数含 --keys 的值，对本机能 docker inspect 的人可见，所以 7880 的防火墙才是真正的边界，不能只靠「别人不知道 key」。另一条：会话 cookie 走 query string，会进日志 / Referer / 浏览器历史，这是为兼容无法自定义 WS 握手头的 SDK 做的让步，README 明写「不要把这个模式推广到 /tk 之类的敏感接口」

  • 边界

    e2e 自己测不到代理路径：e2e.py 的信令直连 ws://127.0.0.1:7880，只有 token 走网关，所以代理路径上的问题它发现不了。systemd unit 文件也不在仓库里（属本机配置）。iPhone 在 CGNAT 后会走 DERP 中继，README 的定性是「能通但慢，不是故障」。自签证书必须是 CA:FALSE 的叶子证书，否则 iOS Safari 的 rustls 会以 CaUsedAsEndEntity 拒掉——而重新生成证书等于 iPhone 上的信任失效

  • 边界

    代码默认值与部署值不一致，README 直说了：ACP_INIT_TIMEOUT_MS 代码里是 12000，但 pi-acp 冷启动常常超过 12 秒会直接超时降级，所以部署时必须设 30000；voicekit-bridge.service 里已用 Environment=ACP_INIT_TIMEOUT_MS=30000 覆盖。其余默认值：ONESHOT_TIMEOUT_MS 90000、SESSION_IDLE_MS 300000、HISTORY_TURNS 4、VOICEKIT_SESSION_HOURS 720

两个 README 都没有 Roadmap / TODO / 路线 一节，仓库也没有 ROADMAP.md，GitHub issue 区 open 与 closed 均为 0 条。所以这里没有「计划」行——「已落地」取自 git log 与工作树抽查，「边界」逐条取自根 README、voicekit/README.md 与 docs/issues/ 台账的原文。没有编造计划项。
