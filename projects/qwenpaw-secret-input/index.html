SEC.01

$做什么

QwenPaw 后端插件。agent 执行到一半需要凭据（推代码、调 API、签请求）时调用 request_secret，人在私有卡片里输入，模型只收到一个一次性 ref。明文保存在插件内存中，secret_exec 在进程内完成替换，工具输出里出现的原值被替换成 ***。

SEC.03

$架构

模型 ──request_secret(label, reason)──► 私有卡片 (overlay / 独立答页)
                                            │ 人输入明文
                                            ▼
                                  插件内存 · 不落盘 · 有 TTL
                                            │
模型 ◄── {"status":"saved","ref":"sr_…"} ───┘

模型 ──secret_exec(ref, cmd)──► 确认卡：完整命令 + cwd ──批准──► 进程内替换 {{secret}} 执行
                                                                       │
                                                                       ▼
                                                              出站中间件：原值 → ***
模型 ──secret_export(ref, env_key)──► 确认卡：env 名 ──批准──► 宿主加密 env 存储
                                                                     后续 shell 用 $ENV_KEY
拒绝 / 超时 / 取消 ──► ref 不消费，仍可用于其他动作

四个 HTTP 端点挂在 /api/secret-input 下，只接受 loopback 或已认证调用方。卡片有两种渲染：阻塞时的 overlay，和一个自包含答页。

SEC.04

$要点

F01
🔑

三个工具

request_secret 阻塞等人并返回一次性 ref。secret_exec 在进程内替换占位符后执行命令。secret_export 把值写入宿主加密 env 存储。

F02
🧽

出站擦洗

一道中间件在工具结果进入 transcript、记忆和磁盘卸载路径之前改写它，作用于所有工具的结果。

F03
🛃

消费前确认

花掉 ref 之前弹确认卡，显示完整命令、工作目录或 env 名。控制字符转义显示，超过 4000 字符的命令在开卡前拒绝。

F04
🚫

确认由插件自带

QwenPaw 2.2.2 上实测 secret_exec 执行时宿主审批列表为空，宿主不拦插件工具，所以这道闸在插件里。

F05
🧊

校验器是冻结证据

packaging/verify_qp_plugin.py 离线运行真实 PluginLoader，测试钉住它的 sha256 并跑 8 个负对照、1 个正对照。

F06
🔴

每条门配负对照

仓库约定每个 gate 都有负对照：删掉防御，测试必须变红。用例只使用显式假值。

SEC.05

$版本与限制

  • v0.2.0

    消费 ref 前的人工确认卡；拒绝、超时、取消不消耗 ref；命令中的控制字符与 bidi 字符转义显示。

  • v0.1.0

    三个工具、出站擦洗中间件、loopback 门、答页与 overlay 卡片，296 条离线测试。

  • 限制

    确认卡提供知情与可见性，不构成沙箱：同机 loopback 进程可以读取待确认项并自行批准。短于 8 字符的值不做出站擦洗。

  • 限制

    CI 只跑 ruff、compileall、node --check 三个静态门，335 条用例依赖宿主包、在本地运行。宿主版本窗口为 QwenPaw 2.1.0 到 2.99.0 之前。
