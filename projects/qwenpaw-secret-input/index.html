SEC.01

$为什么存在

Agent 干到一半需要一个凭据才能收尾——推一个 fix、调一个 API、签一个请求。你不希望这个凭据出现在聊天记录、模型上下文或宿主日志里。这个插件就是那条通道：人在私有卡片里输入，模型自始至终只收到一个一次性 ref。明文只留在插件内存（绝不落盘），secret_exec 在进程内完成替换，任何出现在工具输出里的原值都被擦成 ***。

但它不假装自己是沙箱。README 的威胁模型列了 10 条，第 1 条就是「同机进程隔离不存在」——宿主 agent 能以同一个 uid 跑 execute_shell_command、读宿主 env 存储、printenv；擦洗是 best-effort，编码过、拆开的、改写过的值（echo ${TOKEN:0:4}）抓不到。把边界写在最前面，是这个项目的一部分。

SEC.02

$能力清单

F01
🔑

三个工具

request_secret 阻塞等人、发一次性 ref；secret_exec 在进程内替换 {{secret}} 并把输出擦成 ***；secret_export 是唯一一处刻意的例外——把值写进宿主的加密 env 存储，好让后续 shell 工具用 $ENV_KEY。只用一次就别导出。

F02
🧠

明文只在内存

从不落盘。Python 字符串无法置零，所以内存取证明确不在范围内——TTL 只能把窗口缩小，不能消除。

F03
🧽

出站擦洗中间件

一个中间件在工具结果抵达 transcript、记忆或磁盘卸载路径之前改写它。它是全局的：改的是每个工具的结果，不只是本插件的。所以「重定向到文件再用另一个工具读回来」这条路是被覆盖的。

F04
🛃

消费 ref 前要人点头

两个消费型工具不会自己烧掉 ref。开卡显示完整命令文本加 cwd 与 env_name（导出则显示 env_key），批准后才执行，且只执行一次。{{secret}} 在卡上仍是占位符，只在真正执行那一刻替换。

F05
🚫

看不见的尾部不许批准

控制字符与 bidi 字符转义成 \uXXXX 显示，卡片因此藏不住终端转义、也没法重排文本。超过 4000 字符的命令在开卡之前就被拒（status: "error"，ref 不消费）——不让人去批准一段自己看不完的尾巴。

F06
↩️

拒绝不等于烧掉

declined / timed_out / cancelled 都返回 {"ref": "not_consumed"}：ref 仍然可用，但只能用于另一个动作。人刚拒掉的那条命令，不要原样重试。

F07
🔌

宿主不拦插件工具（实测）

QwenPaw 2.2.2 上实测（2026-10-21）：模型调 secret_exec 直接执行，全程没有任何宿主审批弹窗，/api/approval/list 始终为空。所以消费前的确认闸是插件自己承担的那道，不是借来的。

F08
🪟

四个端点，两种卡片

/api/secret-input 下四个 HTTP 端点，只认 loopback 或已认证调用方。渲染面是一块阻塞时的 overlay 卡加一个自包含答页，两者都能渲染密钥卡与确认卡。

F09
🔒

配置拼错按最严的算

require_consume_approval 默认 true，配置项名字打错时也按 true 处理——fail closed。要恢复直接执行的旧路径得显式写 false，而且只该在每条命令都已在别处审查过的环境里这么做。

F10
🧊

冻结证据，不是产品代码

packaging/verify_qp_plugin.py 离线跑真实的 PluginLoader。tests/test_verifier_gate.py 钉住它的 sha256（2182bc4d…f18a），并跑 8 个负对照加 1 个正对照——改这个校验器、或发布一个它本该拒的包，都会让套件变红。

F11
🔴

不会失败的门不是门

每条 gate 都要求配一个负对照：删掉那道防御，看着测试变红。测试只用显式假值（DUMMY-SK-abcdef123456），从不碰真密钥。335 条用例全部离线可跑。

F12
👤

谁答的卡，记下来

你自己的本地 agent 可以抢在你前面答卡：它能从 loopback 调 GET /card/{id}/meta 拿到 nonce，提交一个它编的值。它读不到自己不知道的明文，但能让插件存进一个假的。所以插件记录并显示应答方与时间（answered by <peer> at <time>），让你能察觉——要高价值凭据时，人在场，提交后回看卡片。

SEC.03

$一次 ref 的一生

模型 ──request_secret(label, reason)──► 私有卡片 (overlay / 自包含答页)
                                          │ 人输入明文
                                          ▼
                            明文只进插件内存 · 绝不落盘
                                          │
模型 ◄──{"status":"saved","ref":"sr_…"}───┘  模型永远看不到明文
   │
   ├─secret_exec(ref, cmd)──► 确认卡：完整命令 + cwd
   │                            │批准
   │                            ▼  进程内替换 {{secret}} → 执行
   │                            ▼  出站擦洗中间件：原值 → ***
   │
   └─secret_export(ref, env_key)──► 确认卡：env 名
                                      │批准
                                      ▼  宿主加密 env 存储 → 后续 shell 用 $ENV_KEY

拒绝 / 超时 / 取消 ──► {"ref":"not_consumed"} ref 仍可用于别的动作
命令 > 4000 字符 ────► 开卡前就拒 不让人批准看不见的尾部

SEC.05

$路线

  • 已落地 v0.1.0

    三个工具（request_secret 阻塞等人 + 一次性 ref、secret_exec 进程内替换 {{secret}} 且输出擦洗为 ***、secret_export 落宿主加密 env 存储）、出站擦洗中间件默认开、loopback / 认证门、自包含 HTML 答页、Console overlay 卡片；296 条离线测试全绿，真机热装验收记录在 docs/verification/2026-10-19-acceptance.md

  • 已落地 v0.1.1

    发布包随带双语 README 与 LICENSE；仅打包变化，插件行为与 v0.1.0 完全一致

  • 已落地 v0.2.0

    消费 ref 前的人工确认卡（完整命令 / cwd / env_name，导出则 env_key）；拒绝超时取消返回 not_consumed；控制字符与 bidi 显示为 \uXXXX、超 4000 字符的命令开卡前拒；默认开启且配置项拼错按 true 处理

  • 边界

    确认卡是知情与可见性机制，不是安全边界：同机 loopback 进程（含 agent 自己的 shell）可以读 /pending、从 /card/{id}/meta 取 nonce、再 POST /answer {"approve": true} 自我批准；同 uid 进程仍可读宿主环境存储。擦洗是 best-effort（威胁模型第 1、10 条）

  • 边界

    secret_exec 本身就是一个外泄原语——命令是模型写的。中间件清的是模型看到的东西，不是它发出去的东西：一次网络发送在任何擦洗发生之前就已经离开机器。所以别让 agent 花掉一个 ref 之前，先看清那条命令（威胁模型第 9 条）

  • 边界

    {{secret}} 写在命令行里就等于把值放进 argv：/proc/<pid>/cmdline 在子进程整个生命周期内是全局可读（0444），同样的文本还会出现在 ps、auditd 的 EXECVE 记录和进程记账里——比「同 uid」宽得多。优先用 $<env_name>。另外短于 8 字符的值完全不做出站擦洗（否则普通输出会被 *** 溅满），所以 6 位密码会原样到达 stdout（威胁模型第 7、8 条）

  • 边界

    三个工具首装默认 disabled，要在 agent 设置里显式打开；只给某一个 agent 打开时，其他 agent 的模型会如实报告工具不存在。宿主版本窗口 QwenPaw ≥ 2.1.0, < 2.99.0，用宿主自带的 Python 3.12。宿主停着时装，本地 zip 会被以 plugin.json not found 拒掉——用目录，或把 zip 挂到 URL 上

  • 边界

    CI 只跑静态门（ruff check + compileall + node --check ui/index.js）。335 条 unittest 会 import 宿主包，因此不在 CI 里，要用宿主解释器在本地跑。工作流里写着：不要为了让 CI 变绿而删断言，要补宿主依赖

仓库没有公开的 Roadmap 一节，issue 区也是空的——所以「已落地」三行取自 v0.1.0 / v0.1.1 / v0.2.0 三份 release notes 的原文，「边界」五行取自 README 的 Threat model（10 条）与 Install / Development 两节。没有编造任何计划项。
